## Acceptance gates

### All-around evaluation rule

Do not publish one blended leaderboard score as the definition of “best.” On every frozen benchmark, report Choice accuracy and per-class/per-domain results; Choice/Noul/Score log loss and Brier score where distributions are meaningful; calibration error with a pinned binning rule and reliability plots; coverage and selective risk at predeclared abstention thresholds; robustness under paraphrase, formatting, irrelevant-context, order and small rule perturbations; and batch-1 latency, peak memory and tokens/second on the same declared hardware and serving setup. Include unanswered/error rates, paired confidence intervals, subgroup slices and the count of regressions. Treat ordinal Score targets separately from categorical probability targets and state what the gold distribution means.

For each benchmark and decision type, keep accuracy within the 5% relative target against the strongest qualifying same-size peer. For probability quality, coverage, robustness and efficiency, show side-by-side results and uncertainty; require non-inferiority margins to be declared before the sealed evaluation. Report a Pareto comparison: a model is “best all around” only if it is not materially worse on any predeclared metric family and improves at least one, or it wins each of the separately declared primary metrics. If intervals are inconclusive, say so. Never select checkpoints, prompts, calibration or training recipes on the sealed set; do not repeatedly tune to public leaderboard items. The set of development metrics is for diagnosis and selection, while only a single frozen candidate and frozen reference proceed to final evaluation.

1. Pin a benchmark and reproducible scorer, candidate and competitor revisions, prompt/serving settings, context limits, precision, coverage, and calibration fitting; compare matching IDs. Record observed runs and public reported results separately. Record refusals and failures, not only answered cases. Compare text-only single-pass systems as the primary cohort; disclose reasoning, multimodal and other variants separately.
2. Search and document competitive same-size Qwen models, including StartLux 0.8B/2B/4B, and evaluate the strongest runnable candidates on the same suite. Freeze the reference and selection rules before final evaluation. If the strongest candidate cannot be run, leave competitiveness unverified rather than silently choosing an easier reference.
   Include widely adopted [Kev 0.8B](https://huggingface.co/jaredpalmer/kev-0.8b), [Decider 2B](https://huggingface.co/Mapika/decider-2b), [Kev 4B](https://huggingface.co/jaredpalmer/kev-4b), and stronger same-size leaderboard candidates; report adoption separately from benchmark performance. Popularity cannot substitute for a measured SOTA reference.
3. Build rights-reviewed, traceable, leakage-screened training and calibration data. Freeze a separate development set and a fresh independently adjudicated test/OOD set with exact and near-duplicate checks against training and public benchmark sources before a candidate is promoted. A separate local pilot on a source with explicit training and license terms may test feasibility while those release gates remain open; it cannot establish SOTA or be published as cleared weights. Human/source rights questions and existing NOT_FOR_TRAINING flags remain binding.
4. Run and record controlled training experiments per size with pinned configuration, base, data hashes, seed, checkpoints, compute and calibration; compare with untuned base and Qev 1.0. Choose on development data only. Do not assume that the prior 1,000-example constraint applies to this new goal, but preserve data rights and document any expanded mixture.
5. Freeze each candidate and evaluate once on the independent test with the selected competitors, reporting same-item accuracy, probability metrics and paired uncertainty intervals. Each Qev tier must achieve >= 0.95 times its strongest qualifying same-tier competitor on the predeclared primary score. Assess meaningful subgroup regressions, unanswered cases, and uncertainty before claiming within 5%.
6. Publish three size-specific tables on Qev GitHub and all three Hugging Face cards; include Qev's current numbers, source links, known gaps, measurement limitations and unknowns. Update these when validated new results replace the baseline. Confirm live rendered files and preserve existing model-card metadata and license caveats.
